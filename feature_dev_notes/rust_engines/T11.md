## What changed

- **`ras2cng/archive_direct.py` (new), wired into `archive_project()`.**
- **Setting:** `RAS2CNG_ARCHIVE_ENGINE` or `--archive-engine`.
  - `auto` (default) is `prefer-native`, except that it stays on Python under `RAS2CNG_GEOPARQUET_WRITER=python`.
  - `native` (aliases `direct`, `terrio`, `rust`) is strict.
  - `python` never tries the direct path.
- **Capability:** `terrio._terrio.write_hecras_archive` and `hecras_archive_layers`.
- **Manifest:** 3.0 when the direct path is active, and each file gets an `archive` record: `path`, `fallback_reason`, `native_layers`, `python_layers`, `refused`, `crs_source`, `seconds`. Without the capability or with `python`, it stays 2.7 with no `archive` key.

### What comes from where

I kept the native set deliberately small.

| Content | Source | Why |
|---|---|---|
| `mesh_cells`, `mesh_faces` | engine | The expensive layers; columns and values equal |
| 2D summary variables | engine | Equal, apart from the refusals below |
| Every other geometry layer, all `*_text` | Python through `extra_layers` | These hold everything T10 found missing, the type differences and the breakline refusal. They read in about 0.1 s per file (g01: 0.11 s; mesh in Python 0.29 s) |
| Refused variable or layer | Python through `extra_layers` | Recorded per file, with `filled` true or false |
| Everything else that goes wrong | Whole file on the Python path | `fallback_reason` is recorded; strict raises, even under `skip_errors` |

**Always on the Python path:** `--no-sort`, `--results-layout variable`, `--results-geometry point|none`, steady plans, a plan whose geometry has no archived `mesh_cells`, and geometry with no HDF. Unsteady cross-section and auxiliary result tables under `results/` are still written by Python, as before.

**Strict mode decisions to check:**
- A refused layer that Python can fill does not raise, because otherwise p07 could never pass (`cell_last_iteration` is always refused).
- Geometry with no HDF and steady plans also do not raise, because the engine has nothing to do for them.

**Guards against silent loss:**
- A file with `mesh_areas` where the engine wrote no mesh layer and gave no refusal falls back.
- A selected variable the engine does not mention is read in Python.
- Rows by layer read back from the written file must match the report.

**CRS:** always passed when any is known. The order is the Python frames' CRS, then the file's stored projection, then the project's. Plans use their geometry file's CRS. With none at all it stays null, as on the Python path.

## Equivalence: full archive, by layer, row and column

Compared the direct output against the pre-change code's output (`scripts/cmp.py`, `scripts/mdiff.py`).

**Tolerance:**
- Exact, except that a float64 value equals a float32 value when narrowing gives the same number. In practice `types` was empty, so this allowance had nothing to excuse.
- NaN equals null.
- Layers with no unique key are compared as multisets with floats rounded to 3 decimals. Geometry files are byte-identical anyway, so this only matters for layers in plan files, and those are keyed.

| Model | Files | Layers compared | Rows | Layers equal | Files byte-identical |
|---|---:|---:|---:|---:|---:|
| Bald Eagle p07 | 18 | 142 | 2,742,429 | 142 | 17 of 18 |
| Bridges | 7 | 25 | 312,689 | 25 | 6 of 7 |
| Davis | 6 | 18 | 33,608 | 18 | 5 of 6 |
| Spring | 3 | 11 | 4,069,039 | 11 | 2 of 3 |
| Spring_BLE | 3 | 14 | 6,310,252 | 14 | 2 of 3 |

No file, layer or non-null column is missing or extra on any model. `hilbert_index` order is identical wherever it was compared, and `geo` CRS JSON is identical on every geometry and plan file.

**Every difference found:**

1. **The plan parquet is the one non-identical file on each model.**
   - It drops the all-null union columns of geometry layers. Columns: p07 191 -> 20; p05 184 -> 20; Davis 86 -> 20; Spring 28 -> 18; Spring_BLE 32 -> 22. None of them held a value.
   - Consequence: `SELECT bc_line_id FROM 'Model.p07.parquet'` used to return nulls and now errors. No ras2cng reader does this, but an outside query could.
   - The order of the remaining columns differs. Row groups are unchanged.
   - Spring_BLE p02 is on Python, but it also read `mesh_cells` back from the archived file, so it dropped the union columns too.
2. **Manifest:** `schema_version`, the `archive` records and `results[].size_bytes`.
3. **Manifest `geometry_type`,** p07 g06 and g08, one layer each: `nan` on the Python path (its first row has null geometry) and `LineString` on the direct path (first non-null). The direct value is the better one, but it is a difference.

**Python path after this change** (`--archive-engine python`) against the pre-change code: every file byte-identical on all five models, manifest 2.7.

**Note on "Python path":** on this wheel the Python path writes through terrio's `write_geoparquet_layers`, because that is its default. That explains the byte-identity, and T03 is the evidence against pyarrow. I did not rerun a pyarrow comparison here.

## Float32 vs float64 on real data (bridges g03)

Native `breaklines` plus a Python frame with `cell_spacing_near` as float64:

```
InvalidArgumentError: GeoParquet: field cell_spacing_near is Float32 in one layer and Float64 in another
```

It raises rather than returning a refusal, and no file is written. Forced through `write_geometry`, it gives the same class of error (`bl_id is Int64 in one layer and Float64 in another`), which is what sends a file to the Python path. The default native set does not meet this on any of the five models. A pinned real-data test covers it.
