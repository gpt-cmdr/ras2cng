## 2. `invalid_cells`

API, from the released 0.110.3 wheel (PyPI, not the `G:\RustDev\src\ras-commander` worktree):
`invalid_cells="repair"|"hull"|"omit"|"raise"` on `map_sloping_profiles`, `map_horizontal_profiles`,
`get_cells_from_plan_hdf`, `map_whole_simulation`, `prepare_sloping_model`, `compare_with_rasmapper`. The record
is `{"schema": "fim-invalid-cells/1", "policy", "count", "cells": [{mesh, cell_id, reason, action,
original_area, fallback_area, pieces, overlap_with, intersects_aoi}]}` in `fim_manifest.json` and
`manifest.attrs["invalid_cells"]`. `"raise"` raises `MeshCellPolygonError` (a `ValueError`). A horizontal cell table
fixes the policy, so mapping must be given the same one.

ras2cng (`ras2cng/fast_map.py`, `mapping.py`, `cli.py`):
- `--fast-map-invalid-cells` (map and map-hdf) / `generate_result_maps(fast_map_invalid_cells=...)` /
  `map_plan|map_whole_simulation|map_boundary(invalid_cells=...)`. `None` (the default) passes nothing, so the
  engine default (`repair`) applies. Unknown values raise `ValueError` before any project work.
- Capability detection: the keyword is passed only when the RasFim method's signature has it. On older
  ras-commander `raise` is accepted, because strict assembly was the old behaviour. Any other explicit policy raises
  `InvalidCellsUnsupported`. That is deliberately not `FastMapUnavailable`, so `with_terrain` does not
  treat it as a terrain refusal and start a HEC-RAS terrain export. The group falls back to RAS Mapper, or raises with
  `--fast-map-strict`.
- Recorded:
  - `MapResult.invalid_cells` maps each fast-map type to its record.
  - `fast_map_manifest.json` has the engine's top-level `invalid_cells`, plus `ras2cng.invalid_cells_policy` and
    `ras2cng.invalid_cells_count`.
  - `fast_map_whole_simulation_manifest.json` has `invalid_cells` and `invalid_cells_policy`.
  - The boundary manifest records it when the (unreleased) boundary API returns it.
  - A non-zero count is printed to the console.
- Real-engine check: bridges p05 and Davis p02 both report `count: 0`. **No local model has invalid cells, so a
  non-empty record has only been exercised with mocks.** Open question: is there a corpus model with bowtie cells
  (the one ras-commander #745 was qualified on) that could be added to `G:\RustDev\data`?
- Not qualified: how RAS Mapper itself renders such cells compared with `repair`. The docs say so.

## 3. Fast-map 0.11 retained state and native TIFF delivery

### Native delivery: adopted

API: `product_writer="native"` on `map_sloping_profiles`. Sloping only. It needs the engine's
`sloping.native_geotiff_outputs` capability. It excludes velocity, templates and floodplain polygons.
ras-commander's `_native_products.deliver` checks the grid, CRS, float32 type, NaN nodata and LZW before
moving the files.

Measured with `RasFim.map_sloping_profiles` on Bald Eagle bridges p05, Max, plain sloping. Terrain was the
priority-1 source TIFF plus Terrain50.hdf, with threads=7 and writer_threads=2. Each run was a fresh process with
three repetitions alternating between the writers. Peak RSS is psutil-sampled over the process and its engine
children. The host was loaded (CPU at 100% from other agents).

| writer | wall (s), 3 runs | median | peak RSS (MiB) | depth / WSE size (bytes) |
|---|---|---|---|---|
| rasterio | 11.90, 10.86, 9.27 | 10.86 | 805-838 | 5,690,599 / 4,618,274 |
| native | 7.75, 11.75, 7.97 | 7.97 | 685-687 | 5,486,449 / 4,415,719 (-3.6% / -4.4%) |

- Equivalence: depth and WSE are **pixel-identical** (24,185,811 px, 973,902 wet, same NaN mask). Both are LZW
  strips (block 1 x 5941) with no predictor and the same transform and CRS.
- COG policy: the native files are the same kind of artifact as before (raw RAS-Mapper-named LZW GeoTIFFs, not COGs).
  Nothing bypasses `ras2cng.cog`: `--cog` still converts through `area_matched_cog`. The COGs built from the two
  writers' depth outputs are **byte-identical** (1,493,750 bytes each).
- End to end, `ras2cng map --plans p05 --no-velocity --fast-map-strict` on a copy of bridges, with
  `--fast-map-writer native` and then `rasterio`: WSE and Depth are identical. The manifest records
  `product_writer` and `terrain_kind=source`. The Davis p02 run with arrival and percent used `auto`, which chose
  `native` on the `source-canonical` terrain.
- ras2cng: `--fast-map-writer auto|native|rasterio` (env `RAS2CNG_FAST_MAP_WRITER`, API `fast_map_writer`).
  - `auto` (default) uses native when ras-commander has `product_writer`, the engine advertises
    `native_geotiff_outputs`, and velocity is not requested. Otherwise it uses rasterio.
  - `native` is strict: it raises `RuntimeError` (not a terrain refusal) when native delivery is unavailable or
    velocity is requested.
  - The capability is checked before the call, because a `FimUnsupportedError` from inside the call would be turned
    into a terrain refusal.
  - `MapResult.fast_map_writer` and `ras2cng.product_writer` in the manifest record the writer.
  - Horizontal and whole-simulation mapping have no writer choice upstream and are unchanged.

### Retained state: not adopted

The fast-map 0.11 / ras-commander #741 retention (LRU of sloping timesteps across reach windows, retained window and
hydraulic caches with `window_cache_mib`/`hydraulic_cache_mib`/`validation_cache_mib`, and a persistent native
session) is only reachable through `RasFim.prepare_sloping_model(...).map_profiles()` and `RasFim.map_catalog`.
ras2cng cannot use it today:
- ras2cng makes **one** Max request per plan. Non-Max profiles go to RAS Mapper, and ras2cng has no AOI tiling, so
  a prepared model has nothing to reuse.
- Prepared models **refuse `terrain_hdf` and velocity** (`_sloping.map_profiles`: "prepared sloping models do not
  support terrain_hdf or velocity"). `terrain_hdf` is ras2cng's default source-terrain path, which skips the 160-240 s
  terrain export.
- Multi-plan runs use a different HDF per plan, so there is no shared prepared state across plans. `map_catalog` jobs
  have no `terrain_hdf` field either.

It becomes useful if ras2cng ever maps timesteps or AOI tiles of one plan (a FIM catalog workflow), or if ras-commander
lets prepared models use the source terrain. This is recorded in CLAUDE.md, AGENTS.md and the `fast_map.py` docstring.
