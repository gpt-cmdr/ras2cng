### Where the NaN-under-numeric-nodata check now happens

It moves into terrio's area-matched builder (`crates/terrio/src/drivers/area_matched.rs`,
`Accumulators::first`), which classifies every level-0 sample once. There are two ways to use it:

- **Recommended (T13):** ras2cng writes with `area_matched_nan_valid=True`.
  - The check is no longer a gate. terrio treats NaN exactly as rasterio's mask and ras2cng's builder do.
  - Measured below: tags identical to the GDAL path, and lossless pixels bit-identical at every level.
  - NaN rasters, which go to GDAL today, then stay on terrio.
- **Alternative:** ras2cng keeps the GDAL fallback for NaN, writes without `nan_valid`, and discards the staged file
  inside `atomic_output` when `report["nan_pixels"] != [0]`.

Either way `nan_pixels` is recorded, so a non-zero count can go into the `OverviewReport` or the manifest.

The harness function `noscan` in `G:\RustDev\tmp\T04\scripts\cogbench.py` is the reference.

   - So an empty raster costs one wasted terrio write.

   Older terrio keeps the scan path.

### Versioning the fork build

Before any fork wheel is shared, give it a distinguishable version: bump `[workspace.package] version` on a
fork-only release commit, or use a PEP 440 local label such as `0.5.0+gpt.1`. Check how maturin renders Cargo
build metadata before relying on the `+` form; I did not verify it. ras2cng's behaviour is capability-detected from
signatures, not versions, so the label is for humans and resolvers only.

### How ras2cng should depend on the fork: options

| Option | Pros | Cons |
|---|---|---|
| A. `[tool.uv.sources] terrio = { git = "https://github.com/gpt-cmdr/terrio", rev = "<sha>", subdirectory = "python" }` | Exact commit pin; nothing to host; trivial to bump | Every `uv sync` on a new machine **compiles terrio from source**: Rust >= 1.90 plus a C toolchain, about 40 min on this host. uv sources are dev-only: they are not in the published ras2cng metadata, and PyPI forbids direct-URL dependencies anyway |
| B. Fork wheels as GitHub Release assets on gpt-cmdr/terrio, pinned with `[tool.uv.sources] terrio = { url = "https://github.com/gpt-cmdr/terrio/releases/download/<tag>/terrio-...whl" }` (one per platform via markers) or `--find-links` | Prebuilt (seconds to install); built by the fork's existing release-build.yml; no new infrastructure | One URL per platform in pyproject; a "release" on the fork needs the user's approval each time; still dev/deploy-only (not in published metadata) |
| C. A private PEP 503 index (GitHub Pages on the fork, or a CLB-hosted index) with `[[tool.uv.index]] name="gpt-cmdr", url=..., explicit=true` and `terrio = { index = "gpt-cmdr" }` | Clean pyproject; uv resolves per platform; `explicit=true` stops it shadowing PyPI for other packages; works for CLB deployments and downstream pipelines (RBFS, LWI) with one index line | Index to host and maintain; versions must be distinguishable from PyPI terrio (local label) |
| D. Publish under another distribution name (e.g. `terrio-gpt`) | Installable from PyPI by anyone | Same import package `terrio`: two distributions owning one module conflict silently if both are installed; it diverges from upstream naming; and it is a public release (needs approval). Not recommended |

**Recommendation:**

- ras2cng's published metadata keeps `terrio>=0.5.0`. Capability detection already degrades to the
  stock-terrio or GDAL paths.
- For CLB development and deployments, use **C**: an explicit uv index serving fork wheels, built by the fork's own
  `release-build.yml`, with a local-labelled version.
- **B** is the low-effort interim if hosting an index is not wanted yet.
- Use **A** only for a developer who already builds Rust, and only to test a specific unmerged commit.
