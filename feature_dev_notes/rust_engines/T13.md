## 1. Storage areas (T06: fast-map #18, ras-commander #757): default when the engine has them

- How it works:
  - `_check_scope` returns the storage-area count. It refuses the count only when `storage_areas_supported()` is false. That check requires `RasFim.supports_storage_areas() is True` and the `storage_areas` keyword.
  - `preflight()` puts the count into the render dict, so products are routed before any terrain work.
  - `map_plan` passes `storage_areas=True` for sloping and `{"wsel_max": "Max"}` for horizontal.
  - `map_whole_simulation` passes `storage_areas=True`.
- These stay on RAS Mapper for storage-area plans:
  - velocity and the derived products (the engine refuses velocity there);
  - duration (the engine refuses it, per `59033d8`);
  - the boundary (the contour method has no level pools).
- Bald Eagle needs the effective terrain here, because 28 storage-area pixels lie outside the priority-1 source.

Through `ras2cng map` (fresh process, peak RSS of the process tree; RAS Mapper 7.0.1 ran on a project copy):

|---|---|---|---|
| WSE + Depth (Max) | 18.7 s / 1.5 GB (effective terrain, native writer) | **12.2 s** / 1.2 GB | WSE and Depth: 1,345,691 px, 0 mask diff, 0 bit diff |
| Arrival + percent (0.5 ft) | **31.3 s** / 1.5 GB | 81.9 s / 1.4 GB | 1,333,183 px, 0 / 0 (T06 refs) |

- Horizontal and slopingPretty storage-area plans were qualified by T06 through RasFim. They were not re-run through `ras2cng map`.

## 2. Native effective terrain (T07: fast-map #19): default, before the HEC-RAS export

Wiring in ras-commander (#788):

- Priority is proven by `_terrain_scope.top_priority_source`. It now also returns `source_groups`.
- Every level-0 mask and the stitch TIN are staged.
- The CRS is checked with `terrain_identity`.
- Modifications are refused **before** the engine runs.
- Output is `ras2fim-batch effective-terrain`, plus a receipt JSON.

In ras2cng, `TerrainResolver.candidates()` now tries, in order:

1. the source TIFF;
2. the CRS-canonical copy (after a CRS refusal only);
3. **effective** (once per terrain HDF per run);
4. the export.

Options: `--no-fast-map-effective-terrain` skips step 3. `MapResult.fast_map_terrain` records `effective`.

Results:

- Bald Eagle Terrain50 via RasFim: 197,179,058 valid px, **0 mask differences**, 8 values differ (stitch-TIN corners, max 1.53 ft), in **7.0 s / 1.39 GB**. The HEC-RAS export takes about 190 s.
- Through ras2cng, the effective terrain carried p07 (storage area) and bridges arrival/duration/percent. The bridges source TIFF is refused for those products, which before T13 cost the HEC-RAS export. All mapped outputs were bit-identical to RAS Mapper.

## 4. Inundation boundary (T08: ras-commander #755, fast-map #5)

- Already wired in ras2cng: `boundary_supported()` detects `RasFim.map_inundation_boundaries`.
- New in T13: boundaries refuse storage-area plans, and non-Max profiles are decided before any terrain work.
- **Gap:** Davis p02, the only local single-source terrain, is refused through ras2cng. The error is `engine terrain CRS differs from rasterio CRS EPSG:2871`.
  - T08 qualified it with a hand-pinned `terrain_crs_fnv1a64`.
  - ras2cng does not guess CRS identities, so without `--fast-map-strict` the boundary goes to RAS Mapper. It took 27 s here.
  - Bridges/p07 Terrain50 has two sources, so its boundary also goes to RAS Mapper.
  - There is therefore **no new end-to-end ras2cng boundary run**. The evidence remains T08's: Davis Max IoU 0.9935, deterministic, not vector parity.
- Open option: a `--fast-map-terrain-crs-hash` passthrough for users who verify the hash themselves.

## 5. COG report (T04: terrio #23): adopted

- `terrio_writes_report()` detects `report_metadata` and `area_matched_nan_valid` on `Raster.write`.
- With both, `_terrio_cog_with_report` makes **no `_scan_area_matched` pass**, and:
  - NaN under a numeric nodata is valid, so those rasters stay on terrio (lossless file identical to GDAL's, `nan_pixels` recorded);
  - stale report tags are stripped from re-COGed sources;
  - the report is still checked (`_check_terrio_written_report`);
  - an empty raster goes to GDAL.
- Older terrio keeps the scan, which is also the oracle in the tests.

## 6. Bounded warp/mosaic (T04): not adopted

- ras2cng has no whole-raster warp left to remove:
  - `terrain._merge_tifs` already reprojects one 512-px destination block at a time;
  - `_reproject_to_match` and `mapping._reproject_tifs` use rasterio band-to-band warps, which GDAL chunks;
  - raster tiles already use terrio's bounded warp, so there is no pixel cap with this terrio.
- The remaining 400 M px cap is the COG writer's. Both the NumPy builder and terrio hold the base level whole, and no fork feature streams it.
- Measured `_merge_tifs` (Bald Eagle two sources, 40 ft) against `terrio.warp([low, high], dst, bilinear, max_memory_mib=512)`:
  - terrio is **3.6-5.1 s vs 19.0 s**, with peak **952 vs 830 MB**;
  - the grid and mask are the same, but **37.2 M of 49.3 M values differ** (3.99 M by more than 1e-3, max 151 ft).
- Not equivalent and no memory gain, so `_merge_tifs` stays on rasterio. Matching it would need terrio to reproduce the first-valid-wins priority fill and GDAL's downsampling bilinear kernel; that was not investigated.
