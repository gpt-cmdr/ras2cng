## The Davis join

**Root cause:** `geometry.merge(attributes, on=index_column)` on `cell_id` or `face_id` alone, since vector results first shipped (`505d188`, 2026-07-15). IDs restart in every 2D flow area. Davis has `DS Channel` (11 cells, 35 faces) and `area2` (2,705 cells, 5,555 faces). Each colliding ID gave four features: two right, two with the other mesh's value, over the same geometry. Hence 2,738 for 2,716 cells, and also **5,660 for 5,590 faces, which T20 did not report**. T20's new join reproduced it on purpose; the pandas join had it too.

**The archive was right.** Every Davis variable checked equals the plan HDF per mesh, max difference 0. `results.py` already joins on `mesh_name` and `cell_id`.

**What was wrong in Davis's tiles** (features carrying the other mesh's value; difference from the true value):

| Variable | Features before / after | Wrong features | Median / max difference |
|---|---:|---:|---:|
| `maximum_water_surface` | 2,738 / 2,716 | 22 | 6.94 / 9.43 ft |
| `minimum_water_surface` | 2,738 / 2,716 | 22 | 9.37 / 11.10 ft |
| `maximum_face_velocity` | 5,660 / 5,590 | 70, 46 with a different value | 0.098 / 1.46 ft/s |
| `minimum_face_velocity` | 5,660 / 5,590 | 70, 0 different | 0 |
| `cell_last_iteration` | 2,738 / 2,716 | 22 | 119 / 6,935 |
| `cell_maximum_water_surface_error` | 2,738 / 2,716 | 22 | 0.005 / 0.007 ft |
| `cell_cumulative_iteration` | 2,738 / 2,716 | 22, 0 different | 0 |

Example, max WSE: `area2` cell 0 is 49.245 ft and also carried 39.813 ft from `DS Channel` cell 0. Which one a viewer showed depended on draw order.

**Fix:** `_index_join_keys`: `mesh_name` plus the ID when both tables have `mesh_name`. Keys not unique on either side raise `ValueError` (the Arrow join hands those to the checked pandas join). An unpaired row or feature raises `RuntimeWarning`. Manifest `rawResult.joinKeys`.

**Checked against the plan HDF through the tiles:** five Davis variables, z13-17, every (mesh, ID) has one value and it is the HDF's: 0 wrong or multi-valued now, 1,120 (per element, value and zoom) on base.

**Other models:** of the ten plan HDFs on hand (AustinOyster, UPGU2, UPGU3, UPGU4, WA2, Bald Eagle p05 and p07, Davis, Spring, Spring_BLE) **only Davis has two meshes.** On the seven archives scanned, every variable pairs one to one with 0 unmatched rows on either side, so nothing is dropped; a manifest 2.6 archive too. `join_columns` joins have no repeated geometry key. **Any published viewer of a multi-mesh model built before this is wrong** and should be rebuilt; I cannot see those from here.

**Behaviour change:** a multi-mesh archive whose result files lack `mesh_name` now errors instead of showing wrong values. None on hand is like that.
