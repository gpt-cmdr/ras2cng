## 1. Mapping

### What changed

- Floors: `ras-commander[full]>=0.116.0` (also the `fast-hdf` and `fast-map` extras), lock
  updated. With 0.116.0 / 0.15.0 and no code change the suite passed as it was: every
  capability string and `RasFim` call ras2cng uses is unchanged.
- **Shear stress** (`fast_map.shear_supported`, `shear_plan`, `map_shear`; `--fast-map-shear`):
  its own engine call, plain sloping and horizontal, `Shear Stress (Max).tif`,
  `fast_map_shear_manifest.json`, engine in `MapResult.engines`.
- **slopingPretty velocity and derived Max** (`with_faces_options`,
  `sloping_pretty_products_reason`): default when the engine record names
  `rasmapper-with-faces-velocity-derived/1`, lists every option the project uses, and
  `RasFim.map_derived_max` takes the options. The `.rasmap` flags go through unchanged.
- **Terrain:** new candidate `export-canonical` (below).
- **Boundaries:** `fast_map_boundary_method` / `--fast-map-boundary-method native-serial`.
- The terrain refusal notes are printed also when every candidate is refused.

### Inundation boundaries

**The release report named in the brief
(`D:\CLB-Dev\fast-map-api-validation\boundary-gap-20261108\RELEASE-RESULTS.md`) could not be
read: this host (CLB-08) has no `D:` drive.** The wording was taken instead from what
ras-commander 0.116.0 publishes in its mapping guide ("Compare native polygons") and release
notes, and from the fast-map 0.15.0 changelog. If the report qualifies more or less than
that guide, `CLAUDE.md` should follow the report.

What those sources say: the native-serial method stays behind `allow_unqualified=True`
("Qualification defaults remain closed"; receipts "keep qualification and native-vector
parity false, even when raw coordinates match"). The Windows x64 checks use plain sloping,
zero-depth contours, original terrain layouts and RAS Mapper's verified serial polygon loop,
and report exact valid geometry and unrounded coordinates on Baxter, Davis (7.0.1), Bald
Eagle (two sources and storage) and Reese; White Oak p19 matches as raw ring bits and has no
valid-vector delivery.

So ras2cng keeps `deterministic` as the default and adds `native-serial` as an opt-in that
says, in the docstring, the manifest and `CLAUDE.md`, that the engine labels it unqualified.

Re-test on this host (`scripts\boundary_run.py`, RAS Mapper 7.0.1 on project copies, Max,
plain sloping):

| Plan | Polygons / holes / vertices | ras2cng native-serial vs RAS Mapper **serial** export | vs RAS Mapper **ordinary** export | Rust end to end | RAS Mapper |
|---|---|---|---|---|---|
| Davis p02 | 274 / 65 / 47,272 | geometry equal, coordinates equal; area difference 3e-13 acre | **not measured: RAS Mapper's ordinary export failed twice** (`NATIVE_FatalError`) | 4.0 s | 44.6 s (serial) |
| bridges p05 (two terrain sources) | 194 / 344 / 108,189 | equal, equal | equal (same parts and holes) | 8.9 s | 8.5 s ordinary, 12.4 s serial |
| Bald Eagle p07 (two sources, storage area) | 117 / 214 / 104,486 | equal, equal | equal (same parts and holes) | 17.2 s | 8.0 s ordinary, 10.8 s serial |

- "Coordinates equal" is `RasFim.compare_inundation_boundaries`'s unrounded comparison
  (ring start, direction and part order aside). The ras2cng GeoJSON was then compared with
  the serial shapefile separately (`shapely` equality, zero symmetric difference).
- Deterministic on Davis, for scale: 66 holes, 405.98 acres, against 408.63 acres and 65
  holes for the serial export; 2.65 acres of it is missing area, almost all one hole. That
  is larger than the 7,400 ft² the notes carried from an earlier comparison with an ordinary
  export, which I could not regenerate (see the failed export above).
- **The peer lead (equal area to 0.0001 acre on three HCFCD plans, with a different
  part/hole split) is neither confirmed nor refuted.** Those plans are not on this host. On
  the two plans where I have RAS Mapper's ordinary shapefile, parts and holes were the same
  as the engine's, so the split was not reproduced here.
- The boundary is not always faster in Rust: on both Bald Eagle plans RAS Mapper was as fast
  or faster. `CLAUDE.md` now says so.

## 2. `--reproject-wgs84`, and the terrain merge

- `mapping._reproject_tifs` is fixed (it now calls `ras2cng.warp.reproject_path`) and raises
  on failure. `tests/test_warp.py::test_reproject_tifs_changes_the_crs` does not mock it and
  passes in all three environments.
- terrio when the installed build has the streaming warp, with `overview="NONE"`; rasterio
  otherwise or when terrio refuses the file. `terrain._reproject_to_match` uses the same
  helper (nothing calls that function today).
- Checked on real rasters from the runs above, EPSG:4326 target:

  | Raster | Grid | Masks | Values |
  |---|---|---|---|
  | Davis `Depth (Max)` (EPSG:2871, HARN) | same | equal | 10 px differ, max 6e-8 |
  | bridges `Depth (Max)` (EPSG:2271) | same | equal | 155 of 854,579 px differ, max 3.8e-6 |

  Timing on rasters this small says nothing (0.6 s against 0.8 s); T31's 3.9x is on
  Terrain50 and was not re-measured.
- terrio warns "best coordinate operation needs a missing grid" for NAD83 State Plane to
  WGS84. The results above equal rasterio's, so both use the same grid-less operation here.
  **A CRS whose accurate transformation needs a datum grid that one library has and the
  other has not was not tested** (NAD27, for example).
- **Terrain merge:** `RAS2CNG_TERRAIN_MERGE_ENGINE=terrio`, off by default, recorded in the
  terrain provenance. A small real test checks grid, nodata and source priority against the
  rasterio path. T31's Bald Eagle comparison (4.44 ft) was not re-run.
- Raster tiles are unchanged; the `pmtiles.md` sentence T31 named is corrected.

## 3. Vector tiles

### Decisions

- `deduplicate=True` on every freestiler tileset.
- **`sort_values=True` only on tilesets without mesh layers.** This departs from T30's spec
  (every tileset), because the measurement T30 asked for came back against it:

  | `sort_values` alone | Bald Eagle p07 | Davis | UPGU3 |
  |---|---:|---:|---:|
  | `geometry-detail.pmtiles` | 14,859,507 -> 15,806,412 (**+6.4%**) | 523,288 -> 540,595 (**+3.3%**) | 75,309,324 -> 77,662,836 (**+3.1%**) |
  | `results-detail.pmtiles` | 52,446,361 -> 54,863,271 (**+4.6%**) | 2,170,173 -> 2,131,080 (-1.8%) | 343,296,815 -> 342,810,665 (-0.1%) |
  | `geometry.pmtiles` | -0.3% | -4.3% | (with dedup) -0.2% |
  | `results.pmtiles` | -0.2% | -3.4% | -1.0% |

  On a mesh layer nearly every value is unique, and the unsorted table follows feature
  order. `deduplicate` alone leaves both mesh tilesets byte-for-byte the same size (no
  duplicate tiles), as T05 and T30 expected. Davis `results-detail` would have gained 39 KB
  from sorting; the rule gives that up. `RAS2CNG_VECTOR_TILE_SORT_VALUES=1` forces it.
- `line_simplify=1.0` on the lines of non-mesh layers, in `geometry.pmtiles` and for results
  joined to lines. Never `mesh_faces` (`ArrowLayer` refuses it; `tile_line_pixels` returns
  None). `keep_short_lines` unchanged.
- tippecanoe: `--drop-rate=1` in `maplibre._run_tippecanoe` and in `pmtiles.py`.
- **`Terrain_Profiles`: kept out of tiles.** Measured on the exact Davis layer set, with the
  new options:

  | Delivery | `geometry.pmtiles` bytes | Text bytes in the column |
  |---|---:|---:|
  | NumPy text (as before) | 1,129,401 | 175,912 |
  | compact JSON, float32 shortest form | 1,028,364 | 78,369 |
  | compact JSON, two decimals | 769,016 | 54,910 |
  | not delivered | **343,964** | 0 |

  Compact JSON is not small: the file is still 2.2 to 3.0 times the size without it,
  because every tile a conduit crosses repeats it at every zoom. Nothing in the viewer
  reads it. It stays in the archive. `Profile_Data` (structures) has the same shape of
  problem and was not measured or changed.
