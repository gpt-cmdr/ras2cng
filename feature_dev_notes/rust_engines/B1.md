# B1: ras2cng 0.12.0 vs 0.13.0 benchmark by mesh size (2026-11-01)

**Purpose:** data for the public chart on https://rascommander.info/cng/.
**Rule:** every number below was measured on this host. None is estimated. A run that did not finish is reported as "did not finish", not given a time.

**Work dir:** `G:\RustDev\work\B1`.
- `results.csv` and `summary.csv`: chart data, **public HEC example projects only**.
- `results_nonhec.csv` and `summary_nonhec.csv`: two larger non-HEC models. Keep them **out of the chart**.
- `results.jsonl`: every raw record, including the disturbed runs that were repeated and the run that timed out.
- Also there: `logs/` (one log per run, plus `equiv.txt`), `scripts/`, `freeze_old.txt`, `freeze_new.txt`, `out/`, `models/`.

## Method

**Host:**
- CPU: Intel i9-11900KF, 8 cores / 8 threads, 3.5 GHz.
- RAM: 63.6 GB, about 30 GB free.
- Disk: models and outputs on G:, a Samsung 850 EVO 2 TB SATA SSD.
- OS: Windows 11 Pro 26200.

**Host load: important for reading the absolute times.**
- The host was **not idle**. Two `explorer.exe` COM-factory processes (not mine) used about 2.6 cores continuously throughout.
- System CPU was 50-60% before nearly every run (`bg_cpu_pct` in `results.jsonl`, sampled over the 3 s before each run).
- No other benchmark or build ran during the series. Benchmarks ran strictly one at a time.
- Within each run, versions alternated: old→new in runs 1 and 3, new→old in run 2. Both versions therefore saw the same load.
- Absolute times on an idle machine would be lower. Ratios are the robust result.

**Driver: `scripts/bench.py`**, run from the B1-new interpreter:
- Each run is a fresh process started with `subprocess.Popen`.
- **Wall time** is `perf_counter` from launch to exit.
- **Peak memory** is the maximum, over 20 ms samples, of the summed RSS (working set) of the root process and all its descendants (psutil).
  - The per-process Windows `peak_wset` is also recorded as a cross-check. It exceeded the sampled tree peak by at most 3.2% in any run, so sampling misses little.
- The output directory was deleted before each run.

**Repetition:**
- 3 runs per cell; the median is reported.
- Five runs were repeated because the host spiked during them: background CPU 70-90%, or a time more than 20% off the other two runs. The repeat replaced the original, and both are in `results.jsonl`. The repeated runs were:
  - Davis tiles_geometry new r1, 3.97 s, repeated at 2.57 s
  - Davis tiles_results new r2, 6.07 s, repeated at 3.75 s
  - Bridges tiles_geometry new r3, 6.81 s, repeated at 4.15 s
  - Spring tiles_geometry new r1, 78.2 s, repeated at 68.7 s
  - Spring_BLE tiles_geometry new r3, 34.4 s, repeated at 28.6 s

**Operations:**
- **archive_results:** `ras2cng archive <copy> <out> --results`. The CLI has `--plans` but no geometry filter, so the one-plan project copy does the restricting.
  - 0.12.0: the Python path (manifest 2.6).
  - 0.13.0: the direct terrio path (manifest 3.0). Mesh and 2D summaries come from the engine, other layers from Python. Spring_BLE p02 falls back wholly to Python, as documented in T11; it still uses the terrio GeoParquet writer.
- **mesh_read:** `scripts/meshread.py` runs `HdfMesh.get_mesh_cell_polygons(<gNN.hdf>)` in a fresh `python -I` process of each venv. This is the call ras2cng's `geometry._extract_mesh_cells` uses.
  - *seconds* is the in-process time of that call only, excluding imports.
  - *peak* is that process's tree peak, including the imports.
  - 0.12.0 reads with h5py. 0.13.0 uses fast-hdf (`engine="auto"`).
- **tiles_geometry:** `ras2cng maplibre <archive> <out> --geometry-hdf gNN=<copy>/…gNN.hdf --scratch-dir …` with default zooms 0-17. The input is that version's own run-1 archive, i.e. the end-to-end pipeline of each release.
- **tiles_results:** the same command plus `--vector-results`, which publishes the joined 2D result layers.
- **Vector tiler:** tippecanoe is not installed, so both versions' `auto` resolved to freestiler. I checked this with `vector_tiler_backend()` in each venv.
  - 0.12.0: PyPI freestiler 0.3.0. Layers go through an NDGeoJSON round trip (written, read back, then `freestile`).
  - 0.13.0: fork freestiler 0.3.0.1 with Arrow input (`freestiler_capabilities()['arrow'] = True`).
- **30-minute rule for c:** runs had a 1800 s kill timeout. If 0.12.0 run 1 was killed, the remaining runs of that cell were skipped.
- **Mapping:** not benchmarked, as instructed.

## Equivalence (archive run 1, old vs new; `scripts/equiv.py`, `logs/equiv.txt`)

**Same results in both versions:**
- **Geometry and plan GeoParquet files have the same layers and the same rows per layer on all five models.** Totals:
  - Davis: 8,575 geometry / 24,760 plan rows
  - Bridges: 79,373 / 232,862
  - p07: 264,351 / 789,797
  - Spring: 1,104,855 / 2,963,992
  - Spring_BLE: 1,370,639 / 4,939,212
- The auxiliary result tables present in both versions (pipe and SA/2D structure summaries) also have equal rows.

**Expected differences:**
- Manifest schema 2.6 → 3.0.
- Geometry files: 4 flat `bbox_xmin…` columns become one GeoParquet 1.1 `bbox` struct (−3 columns).
- Plan files drop the all-null union columns of geometry layers and add `bbox` and `is_ghost_cell`, as documented in T11:
  - p07: 193 → 20 columns
  - Bridges: 186 → 20
  - Davis: 88 → 20
  - Spring: 30 → 18
  - Spring_BLE: 34 → 22
- Archive sizes are smaller in 0.13.0:
  - p07: 21 → 18 MB
  - Bridges: 9.6 → 9.1 MB
  - Spring: 234 → 210 MB
  - Spring_BLE: 223 → 196 MB
  - Davis is the exception: 0.7 → 1.0 MB, because 0.13.0 adds its pump/1D-structure tables and metadata.

**0.12.0 fails to write its project metadata (old-version bug):** with its era dependencies, the project metadata Parquet (`<Project>.parquet`) is a **0-byte file on every model**. The log says `Project metadata export failed: Cannot write struct type 'rasmap_field_errors' with no child field to Parquet`. 0.13.0 writes it. So 0.12.0 skips that write's work, which slightly *favours* 0.12.0's times.

**Davis only, extra tables in 0.13.0:** it also writes `results/p02/one_d_structure_summary.parquet` and `pump_station_summary.parquet`, which 0.12.0 does not produce.

**Tiles:**
- Both versions publish the same geometry and mesh-result layers.
- On Davis, 0.13.0 also publishes 3 sparse pipe/pump result layers (10 vs 7 result layers), which come from the extra archive tables.
- Tile bytes were not compared; freestiler versions and feature-ID defaults differ, as documented in T12.

## Caveats

1. **Absolute times are from a loaded host:** about 2.6 of 8 cores were busy in `explorer.exe` throughout. Speedups are more robust than seconds.
2. **No HEC example data point above 87k cells.** The chart should stop at 87k, or show the Spring points in a clearly separate, labelled series if the user approves using them. Spring's provenance is unverified.
3. **"0.12.0" means 0.12.0 with its release-date dependencies.** Part of the speedup comes from dependencies, not ras2cng code: ras-commander 0.104 (h5py) → 0.113 with fast-hdf, PyPI freestiler 0.3.0 → fork 0.3.0.1, plus terrio. That is the point of the comparison, but say so.
   - These old archive times are slower than T11's "Python path" figures (p07 29 s there vs 31.5 s here; Spring 22 s vs 98 s). T11's Python path already used ras-commander 0.113 with fast-hdf.
4. **Mesh read times are the call only.** Process start and imports (about 1 s in either venv) are excluded. Peak memory includes them.
5. **Tiles use each version's own archive as input:** the end-to-end pipeline, not an isolated tiler comparison.
6. **The p07 vector-results speedup is a lower bound.** 0.12.0 was killed at 1,800 s and has no completion time; that run was not repeated, per the 30-minute rule. 0.13.0 has 3 normal runs.
7. **The archive outputs of the two versions are not identical:** see *Equivalence*, notably 0.12.0's empty metadata file.
