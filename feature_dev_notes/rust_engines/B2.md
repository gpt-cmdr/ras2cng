# B2: ras2cng 0.12.0 vs 0.13.0 on FEMA eBFE models (2026-11-01/02)

**Purpose:** extend B1 (`B1.md`) above 87k cells using FEMA-delivered eBFE models with their delivered 2D results.
**Rule:** every number below was measured on this host. A run that did not finish is reported as "did not finish", never given a completion time. Skipped cells say why.

**Work dir:** `G:\RustDev\work\B2` (B1's files were not modified).
- `results.csv`, `summary.csv`: B1's schema plus `source` ("FEMA eBFE"), `study`, `huc8`, and `flag`.
  - `flag` marks rows dominated by one huge land-cover polygon (see *UPGU tiles pathology*).
  - `results.csv` also includes runs that did not finish: `backend_note` starts with `GUARD:`, and `seconds` is the kill time.
- `results.jsonl`: every raw record, including originals of repeated runs and guard-killed runs.
- `guards.jsonl`: host-protection kills.
- `skips.jsonl`: skipped runs, with the reason.
- `progress.md`: running log, including every decision and incident.
- `logs/`: one log per run, plus `equiv.txt`.
- `prof/`: profiles.
- Scripts in `scripts/`:
  - `run_b2.py`: the driver.
  - `summarize_b2.py`: B1's `summarize.py` adapted.
  - `prof_layers.py`: the per-layer tiling profiler.

## Versions and method

**Versions:** the same venvs as B1, checked unchanged against B1's freezes (only name-normalisation differences).
- `B1-old`: ras2cng 0.12.0 + ras-commander 0.104.0, with release-date dependencies.
- `B1-new`: ras2cng 0.13.0 + ras-commander 0.113.0 / fast-hdf 0.3.0, plus fork terrio 0.5.0.1 and freestiler 0.3.0.1.
- tippecanoe is absent, so both versions tile with freestiler:
  - 0.12.0: PyPI freestiler via NDGeoJSON.
  - 0.13.0: the fork freestiler with Arrow input.
- No `RAS2CNG_*` environment variables were set.

**Method:** identical to B1, using B1's `bench.py` and `meshread.py` unchanged.
- Each run is a fresh process.
- Wall time is measured from launch to exit.
- Peak memory is the summed RSS of the process tree, sampled every 20 ms.
- mesh_read reports the call time only.
- 3 runs per version; old→new in rounds 1 and 3, new→old in round 2.
- One run at a time; each model was finished before the next one started.
- Tiles inputs are each version's own run-1 archive.

**Changes from B1:**
- **4 h per-run cap** (was 30 min). No run reached it.
- **Host-protection guard** (added in B2): the driver kills the measured tree if G: free space falls below 35 GB or host available RAM falls below 2 GiB.
- **Repeats of disturbed runs:** runs of 30 min or less were re-run once if they were >20% off the mean of the other two runs (when those two agreed within 10%), or if background CPU was ≥80%. The repeat is used and the original kept in `results.jsonl`. Four repeats:
  - UPGU3 archive 0.12.0 r2: 104.3 s at bg 93%, repeated at 97.4 s.
  - UPGU4 archive 0.13.0 r1: 47.7 s, repeated at 35.4 s.
  - UPGU4 mesh read 0.12.0 r1: bg 86%, 60.0 s → 59.5 s.
  - UPGU4 mesh read 0.13.0 r2: bg 81%, 2.01 s → 1.85 s.
- **Stuck alert:** an alert fired if a run made no CPU or I/O progress for 20 minutes. It never fired.

**Host:** the same as B1 (i9-11900KF, 8 cores; 63.6 GB RAM, about 30–32 GB free; Samsung 850 EVO SATA SSD; Windows 11 26200).

**Host load: absolute times are inflated.**
- Background system CPU before each run (`bg_cpu_pct`): median **57%**, range 47–93% over 46 runs; 5 runs were at 70% or more.
- B1 saw about the same (median 56%). The cause is the same `explorer.exe` COM-factory processes, about 2.6 of 8 cores.
- Versions alternated within each round, so both saw the same load. **Speedups are the robust result; absolute seconds would be lower on an idle machine.**
- The load never dropped enough during the series to justify re-running rounds.

## UPGU tiles pathology (investigation, `prof/`)

UPGU3 tiles_geometry took about 28 minutes in **both** versions. B1 measured 68 s for 0.13.0 on Spring (340k cells), so I profiled UPGU3 outside the benchmark, with the driver suspended.

**Where the time went:**
- cProfile (`prof/tiles_new.prof`): 1,612 of 1,625 s are inside freestiler `_LayeredTiler.add_arrow_layer`.
- The path was 0.13.0's normal fork-freestiler Arrow input. There was no GeoJSON fallback and no CRS refusal; the CRS is EPSG:2278, as for Spring.

**Per layer** (`scripts/prof_layers.py`, `prof/u3_layers.txt`):
- **`mannings_n_regions`: 1,534 s** (6,991 CPU-s, about 4.5 cores) of 1,564 s.
- Every other layer took ≤6.3 s: mesh_cells 3.0 s, mesh_faces 4.2 s, model extents 5.4 s.
- On Spring the whole run took 62.6 s, and it has no such layer.

**Cause:**
- The geometry HDF's `Geometry/Land Cover (Manning's n)` is **one polygon with 1,062,037 vertices**. It is thin and convoluted: 40 km² of area over a 33 × 32 km extent.
- ras2cng publishes it as a sparse layer in `geometry.pmtiles` at z0–17, so the tiler clips a 1M-vertex polygon into every tile at every zoom.
- UPGU4 has the same kind of polygon (533,600 vertices). Spring and Spring_BLE have none.

**Classification:**
- This is not a fallback and not a crash: the output is correct.
- It is a tiler scaling pathology (one huge feature) combined with ras2cng's choice to tile that layer over z0–17 without simplifying it or giving it a zoom floor. **Worth a follow-up issue; not fixed here.**
- The UPGU3 tiles_geometry rows are kept as real end-to-end measurements, but are flagged (`flag`), because they measure this polygon, not the mesh.
- UPGU3 tiles+results and both UPGU4 tiles operations were skipped for the same reason, by coordinator decision. The in-flight UPGU3 tiles+results 0.12.0 run 1 was killed after 6 minutes and discarded; no record was written.

## Caveats

1. **Host load:** median background CPU was 57%, so absolute times are inflated. Use the ratios.
2. **"0.12.0" includes its release-date dependencies** (h5py reads, PyPI freestiler via GeoJSON), as in B1.
3. **The UPGU3 tiles rows measure one land-cover polygon, not the mesh.** Do not use them as scaling points.
4. **UPGU4 archive 0.12.0 "did not finish" depends on this host's free RAM** (about 32 GB). It was not run to completion with more memory.
5. **B1's inference that 0.12.0 tiles+results would not finish on Spring/Spring_BLE is now refuted by measurement:** 18 and 29 minutes.
6. **Driver incidents**, all logged in `progress.md`:
   - The driver was restarted for each scope change.
   - It crashed once on a psutil race, between runs; the in-flight run completed and recorded itself.
   - The guard initially killed `bench.py` too (fixed).
   - A skip patch failed to apply, so UPGU4 archive 0.12.0 ran 3 times instead of 1. All 3 hit the RAM guard.
   - None of these affected a recorded measurement.
7. **Elapsed time:** about 7.0 h for the series (18:55 to 01:56), plus about 15 minutes of setup.
