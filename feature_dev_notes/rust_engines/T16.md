## The suspected cause was wrong

The brief suspected low zooms clipping full-resolution vertices. Profiling UPGU3 land cover at 1 ft (122,121 vertices, old engine, z0-17):

| Zoom | Tiles in bbox | Tiles with a feature | Time |
|---|---:|---:|---:|
| z0-z9 (total) | 1 each | 1 each | under 0.5 s |
| z14 | 256 | 190 | 1.7 s |
| z15 | 992 | 555 | 7.0 s |
| z16 | 3,843 | 1,387 | 26.4 s |
| z17 | 15,250 | 3,344 | 110.0 s |

- 75% of the run is z17. Low zooms are almost free, so per-zoom simplification alone would have saved almost nothing.
- The cost is `clip::clip_polygon`: `geo::BooleanOps::intersection` sweeps the **whole ring once per tile in the bounding box**, so cost is vertices x tiles. That explains T15's linear time in vertices.
- Per tile, on one thread, it takes 26-45 ms at z14-z17 and is 99.9% of the tile's work. Snapping and encoding are under 0.1 ms.
- 78% of z17's tiles end up with no feature, and they still paid for the sweep.

The speed comes from the tile tree. Simplification delivers the size reduction.

## What was built

New `freestiler-core/src/polygon_zoom.rs`. For each zoom:

1. **Simplify once for the zoom.** One Douglas-Peucker pass in Web Mercator ranks every vertex, and a zoom keeps the ranks above its tolerance. Every tile of a zoom cuts the same ring, and error does not accumulate over zooms. The layer's max zoom keeps every input vertex.
2. **Cut down a tile tree.** Sutherland-Hodgman clips each ring from a tile into its children. Empty branches are never visited.
3. **Clean each fragment** with the regular path's `BooleanOps::intersection`, now on a few vertices.

No feature is dropped: a ring keeps at least three vertices, and a feature with no area left at a zoom keeps its collapsed ring, which the encoders write as a one-pixel square.

**Default-path fix:** none. The regular path cannot take a reduced input and stay byte-identical, so a large polygon without the option stays slow.

## For ras2cng

- **Option:** `freestiler.FreestileLayer(input=..., crs=..., geometry_column=..., polygon_simplify=<tile pixels>)`, or `freestile_layer(..., polygon_simplify=)`. `_run_freestiler_arrow` already builds a `FreestileLayer` per layer, so the change is small. Range: above 0 and at most 64; anything else raises `ValueError`.
- **Capability check:** `"polygon_simplify" in inspect.signature(freestiler.FreestileLayer).parameters`.
- **Never set it on `mesh_cells` or `mesh_faces`.** Polygons are simplified independently, so shared edges stop being coincident.
- **Install:** `pip install freestiler==0.3.0.2 --find-links https://github.com/gpt-cmdr/freestiler/releases/expanded_assets/v0.3.0.2-gpt-cmdr`
- **Which tolerance is your decision.** See *Tolerance* below. 0.5 is the one that meets "about one tile pixel"; 1.0 is what the brief described and is 7.5% smaller.

Not only land cover benefits: Spring `mesh_areas` (one polygon, 8,621 vertices) took 27.4 s on the regular path and 1.58 s with the option, on a loaded host.

### Reading the results

- **Vertices:** from z8 they stay within 0.70 px of the input, the snapping error. At z4-z6 the worst is 1.61 px.
- **Fill differences:** regions at most about 1.6 px wide at tolerance 1. The old path is under 0.9 px from z8.
- **Fill Hausdorff is above 1 px.** It reaches 28.5 px here, 36.2 px on UPGU4 at z6, and 119.5 px on UPGU3 0.1 ft at z16. These are fingers narrower than a pixel whose two sides collapse together, so they are long in tile pixels and thin. At z14, 28.5 tile pixels is 1.8 CSS px long and under 0.1 CSS px wide.
- **The old path loses fingers too.** Against the input it reaches 717 px at z13, the same finger as the new path's. So this metric's maximum mostly measures sub-pixel slivers in the input.
- **Area is biased low at mid zooms,** where the old path is not: -7.3% vs -0.05% at z8, -2.6% vs -0.02% at z10, -0.42% vs -0.005% at z13. These polygons are thin networks, so a sub-pixel shift is a large share of their fill.
- **z0-z7 percentages are noise.** The polygon is a few hundred to a few thousand px² there, and the old tiles are off by +259% at z0 too.
- **Tile seams, UPGU3 1 ft:** within the shared buffer strip, neighbouring tiles agree to 1.81 px at z14 and below (old: 1.00). At z15-z17 both paths measure the same 1.73-3.42 px.
- **Metric artifact:** the boundary Hausdorff on UPGU4 0.1 ft at z16 shows 5,787 px, because one side had no boundary in that tile. Its fill Hausdorff is 11.25 px.

## Fell short

1. **Fill Hausdorff at or below about one pixel is not met.** The simplified ring is within tolerance and the fill difference is thin, but the Hausdorff maximum is well above 1 px, as it is for the old path. At tolerance 1 the difference width is about 1.6 px, so 0.5 is the setting that meets "about one tile pixel" by width.
2. **Linux wheels were not run.** Docker's daemon was not running and I did not start it. CI built them and I confirmed each wheel's module carries the option. The Windows cp312 wheel was run and tested, and installs from the release URL.
